# 1. What is OOP?

**OOP = Object-Oriented Programming.**

Instead of writing a program mainly as a sequence of functions, we model the program using **objects**.

An object contains:

```text
State       → data/properties
Behavior    → methods/actions
```

Example:

```java
class Car {

    String color;
    int speed;

    void accelerate() {
        speed += 10;
    }

    void brake() {
        speed -= 10;
    }
}
```

Here:

```text
Car
 ├── color  → state
 ├── speed  → state
 ├── accelerate() → behavior
 └── brake()      → behavior
```

An actual car object can then be created:

```java
Car car = new Car();
```

This becomes extremely important in Spring because Spring applications are largely built around **objects managed by the Spring container**.

---

# 2. Class

A **class is a blueprint/template for creating objects.**

```java
class Employee {

    String name;
    int salary;

    void work() {
        System.out.println(name + " is working");
    }
}
```

The class itself defines what an employee object will have.

```java
Employee emp;
```

This declares a reference.

It doesn't create the object yet.

---

# 3. Object

An object is an **instance of a class**.

```java
Employee emp = new Employee();
```

Break this down carefully:

```java
Employee emp = new Employee();
```

### `Employee`

Reference type.

### `emp`

Reference variable.

### `new Employee()`

Creates the actual object.

Conceptually:

```text
Stack                  Heap

emp  ────────────────> Employee object
                         name
                         salary
```

This distinction between **reference and object** is very important for Java and Spring.

---

# 4. Reference Variables

This is one of the most important Java concepts.

```java
Employee e1 = new Employee();
Employee e2 = e1;
```

There is only **one Employee object**.

```text
e1 ─────┐
        ├────> Employee Object
e2 ─────┘
```

Therefore:

```java
e1.name = "Jayesh";

System.out.println(e2.name);
```

Output:

```text
Jayesh
```

Both references point to the same object.

---

# 5. Constructor

A constructor initializes an object when it is created.

```java
class Employee {

    String name;
    int salary;

    Employee(String name, int salary) {
        this.name = name;
        this.salary = salary;
    }
}
```

Create:

```java
Employee emp = new Employee("John", 50000);
```

Constructor executes during object creation.

```text
new Employee(...)
       ↓
constructor
       ↓
object initialized
```

---

# 6. Default Constructor

If you don't define any constructor:

```java
class Employee {
}
```

Java provides a default no-argument constructor.

So:

```java
Employee e = new Employee();
```

works.

But if you define your own constructor:

```java
class Employee {

    Employee(String name) {
    }
}
```

Java **doesn't automatically provide** the no-argument constructor.

Therefore:

```java
new Employee();
```

will fail.

---

# 7. Constructor Overloading

A class can have multiple constructors with different parameters.

```java
class Employee {

    Employee() {
    }

    Employee(String name) {
    }

    Employee(String name, int salary) {
    }
}
```

This is **constructor overloading**.

It is a form of **compile-time polymorphism**.

---

# 8. `this` Keyword

`this` refers to the **current object**.

Example:

```java
class Employee {

    String name;

    Employee(String name) {
        this.name = name;
    }
}
```

Without `this`:

```java
name = name;
```

Java can't distinguish the instance variable from the parameter.

With:

```java
this.name = name;
```

means:

```text
current object's name = constructor parameter name
```

# 9. Methods

Methods define object behavior.

```java
class BankAccount {

    double balance;

    void deposit(double amount) {
        balance += amount;
    }

    void withdraw(double amount) {
        balance -= amount;
    }
}
```

Usage:

```java
BankAccount account = new BankAccount();

account.deposit(1000);
account.withdraw(200);
```

# 10. Method Parameters and Return Values

```java
int add(int a, int b) {
```

Calling:

```java
int result = add(10, 20);
```

Important concepts:

* parameter
* argument

* return value
* `void`

# 11. Encapsulation ⭐

One of the four major OOP principles.

The four commonly discussed principles are:

```text
1. Encapsulation
2. Inheritance
3. Polymorphism
4. Abstraction
```

Encapsulation means **bundling data and behavior together while controlling access to the object's internal state.**

Bad:

```java
class BankAccount {

    public double balance;
}
```

Anyone can do:

```java
account.balance = -500000;
```

Better:

```java
class BankAccount {

    private double balance;

    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    public double getBalance() {
        return balance;
    }
}
```

Now:

```text
balance
   ↓
private
   ↓
cannot directly access
   ↓
controlled through methods
```

This is extremely important in enterprise Java.

# 12. Access Modifiers

You must know these very well.

| Modifier    | Same Class | Same Package | Subclass | Everywhere |
| ----------- | ---------: | -----------: | -------: | ---------: |
| `private`   |          ✅ |            ❌ |       ❌* |          ❌ |
| default     |          ✅ |            ✅ |        ✅ |          ❌ |
| `protected` |          ✅ |            ✅ |        ✅ |          ❌ |
| `public`    |          ✅ |            ✅ |        ✅ |          ✅ |

Example:

```java
private String password;
```

is accessible only inside the class.

# 13. Getters and Setters

Common encapsulation technique:

```java
class Employee {

    private String name;
    private int salary;

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public int getSalary() {
        return salary;
    }

    public void setSalary(int salary) {
        this.salary = salary;
    }
}
```

But remember:

> Encapsulation does NOT simply mean "generate getters and setters."

Good encapsulation means controlling how internal state can be accessed or modified.

# 14. Inheritance ⭐

Inheritance allows one class to acquire properties and behavior from another class.

```java
class Animal {

    void eat() {
        System.out.println("Eating");
    }
}
```

Child:

```java
class Dog extends Animal {

    void bark() {
        System.out.println("Barking");
    }
}
```

Now:

```java
Dog dog = new Dog();

dog.eat();
dog.bark();
```

`Dog` inherited `eat()`.

Relationship:

```text
Animal
   ↑
   |
  Dog
```

This represents:

> Dog IS-A Animal.

---

# 15. Types of Inheritance in Java

### Single inheritance

```text
Animal
   ↑
  Dog
```

### Multilevel inheritance

```text
Animal
   ↑
  Dog
   ↑
 Puppy
```

### Hierarchical inheritance

```text
       Animal
       /    \
     Dog    Cat
```

### Multiple inheritance through classes

Java does **not** support:

```java
class C extends A, B
```

because of ambiguity problems.

However, Java supports multiple inheritance of **type through interfaces**:

```java
interface A {}
interface B {}

class C implements A, B {}
```

# 16. `super` Keyword

`super` refers to the parent class.

Example:

```java
class Animal {

    String name = "Animal";
}
```

```java
class Dog extends Animal {

    String name = "Dog";

    void print() {
        System.out.println(name);
        System.out.println(super.name);
    }
}
```

Output:

```text
Dog
Animal
```

You can also use:

```java
super.method();
```

and:

```java
super();
```

to invoke parent constructor.

---

# 17. Method Overriding ⭐

Child class provides its own implementation of a parent method.

```java
class Animal {

    void sound() {
        System.out.println("Animal sound");
    }
}
```

```java
class Dog extends Animal {

    @Override
    void sound() {
        System.out.println("Bark");
    }
}
```

Now:

```java
Dog dog = new Dog();

dog.sound();
```

Output:

```text
Bark
```

This is **method overriding**.

It is fundamental to runtime polymorphism.

---

# 18. `@Override`

Always prefer:

```java
@Override
void sound() {
}
```

Why?

The compiler verifies that you're actually overriding a parent method.

Without it, you could accidentally create a new method due to a signature mistake.

# 19. Polymorphism ⭐⭐⭐

Polymorphism means:

> One interface/reference can represent different object implementations.

There are two major forms you need to understand.

```text
Polymorphism
│
├── Compile-time
│   └── Method Overloading
│
└── Runtime
    └── Method Overriding
```

---

# 20. Compile-Time Polymorphism

Example:

```java
class Calculator {

    int add(int a, int b) {
        return a + b;
    }

    int add(int a, int b, int c) {
        return a + b + c;
    }
}
```

Same method name:

```text
add(int,int)
add(int,int,int)
```

Compiler determines which method to call.

Therefore:

> Method overloading = compile-time polymorphism.

---

# 21. Runtime Polymorphism ⭐⭐⭐

This is much more important for Spring.

```java
class Animal {

    void sound() {
        System.out.println("Animal");
    }
}
```

```java
class Dog extends Animal {

    @Override
    void sound() {
        System.out.println("Dog");
    }
}
```

Now:

```java
Animal animal = new Dog();

animal.sound();
```

Output:

```text
Dog
```

Why?

Because:

```text
Reference type → Animal
Actual object  → Dog
```

Java chooses the overridden method based on the **actual object at runtime**.

This is called:

> Dynamic method dispatch / runtime polymorphism.

---

# 22. Reference Type vs Object Type ⭐⭐⭐

You absolutely need this before Spring.

```java
Animal animal = new Dog();
```

Two different concepts:

```text
Animal → reference type
Dog    → object type
```

The reference determines what methods are **accessible at compile time**.

The actual object determines which overridden implementation executes at runtime.

# 23. Upcasting

```java
Dog dog = new Dog();

Animal animal = dog;
```

or:

```java
Animal animal = new Dog();
```

This is upcasting.

```text
Dog
 ↑
Animal reference
```

Generally safe and implicit.

---

# 24. Downcasting

```java
Animal animal = new Dog();

Dog dog = (Dog) animal;
```

This is downcasting.

It requires explicit casting.

But:

```java
Animal animal = new Cat();

Dog dog = (Dog) animal;
```

causes:

```text
ClassCastException
```

Therefore understand casting carefully.

---

# 25. `instanceof`

Before downcasting:

```java
if (animal instanceof Dog) {
    Dog dog = (Dog) animal;
}
```

Modern Java also supports pattern matching:

```java
if (animal instanceof Dog dog) {
    dog.bark();
}
```

# 26. Abstraction ⭐⭐⭐

Abstraction means exposing **what an object does** while hiding unnecessary implementation details.

For example:

```java
interface PaymentService {

    void pay(double amount);
}
```

The caller knows:

```text
pay()
```

but doesn't need to know the internal payment implementation.

---

# 27. Abstract Class

```java
abstract class Animal {

    abstract void sound();

    void eat() {
        System.out.println("Eating");
    }
}
```

Child:

```java
class Dog extends Animal {

    @Override
    void sound() {
        System.out.println("Bark");
    }
}
```

You cannot do:

```java
new Animal();
```

because it's abstract.

---

# 28. Abstract Method

```java
abstract void sound();
```

An abstract method has no implementation in the abstract class.

The child must provide implementation unless the child is also abstract.

# 29. Interface ⭐⭐⭐⭐⭐

This is one of the most important concepts for Spring.

```java
interface PaymentService {

    void pay(double amount);
}
```

Implementation:

```java
class CreditCardPayment implements PaymentService {

    @Override
    public void pay(double amount) {
        System.out.println("Credit card payment");
    }
}
```

Another:

```java
class UPIPayment implements PaymentService {

    @Override
    public void pay(double amount) {
        System.out.println("UPI payment");
    }
}
```

Now:

```java
PaymentService payment = new UPIPayment();

payment.pay(1000);
```

This is the foundation of a very important Spring pattern:

```text
Interface
   ↓
Implementation
   ↓
Spring injects implementation
   ↓
Service uses interface
```

---

# 30. Interface vs Abstract Class

Know this comparison.

| Interface                                      | Abstract Class                         |
| ---------------------------------------------- | -------------------------------------- |
| `implements`                                   | `extends`                              |
| Multiple interfaces possible                   | Only one class can be extended         |
| Defines a contract/type                        | Can provide shared base implementation |
| Fields are implicitly `public static final`    | Can have instance fields               |
| Methods can be abstract/default/static/private | Can have abstract + concrete methods   |
| Very useful for loose coupling                 | Useful for shared base behavior        |

Modern Java interfaces can contain:

```java
default
static
private
```

methods too.

So don't think:

> Interface = only abstract methods.

That's outdated.

# 31. Composition ⭐⭐⭐⭐⭐

This is extremely important for Spring.

Composition means one class **contains/uses another object**.

```java
class Engine {

    void start() {
        System.out.println("Engine started");
    }
}
```

```java
class Car {

    private Engine engine;

    Car(Engine engine) {
        this.engine = engine;
    }

    void startCar() {
        engine.start();
    }
}
```

Here:

```text
Car
 │
 └── Engine
```

Car **HAS-A** Engine.

This is composition.

---

# 32. Inheritance vs Composition

Very important interview concept.

### Inheritance

```text
Dog IS-A Animal
```

```java
class Dog extends Animal
```

### Composition

```text
Car HAS-A Engine
```

```java
class Car {
    private Engine engine;
}
```

In modern application design, composition is often preferred over inheritance when you simply want to reuse behavior.

---

# 33. Association

Association means two objects are related.

```java
class Teacher {
}
```

```java
class Student {

    private Teacher teacher;
}
```

There is a relationship:

```text
Student ───── Teacher
```

Neither necessarily owns the lifetime of the other.

---

# 34. Aggregation

Aggregation is a weaker **HAS-A** relationship.

Example:

```java
class Department {

    List<Employee> employees;
}
```

Employees can theoretically exist independently of the department.

```text
Department
   |
   ├── Employee
   ├── Employee
   └── Employee
```

---

# 35. Composition vs Aggregation

### Composition

Strong ownership.

```text
House
 └── Room
```

If the conceptual parent is destroyed, the contained object generally has no independent lifecycle in that model.

### Aggregation

Weak relationship.

```text
University
 └── Student
```

Students can exist independently of a particular university.

# 36. Dependency

A class depends on another class when it needs that class to perform its work.

```java
class OrderService {

    private PaymentService paymentService;

    OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

`OrderService` depends on:

```java
PaymentService
```

This concept leads directly to:

# Dependency Injection

which is one of the most important Spring concepts.

---

# 37. Dependency Injection ⭐⭐⭐⭐⭐

Without DI:

```java
class OrderService {

    private PaymentService paymentService =
            new CreditCardPayment();
}
```

Problem:

`OrderService` creates its own dependency.

It's tightly coupled.

Better:

```java
class OrderService {

    private PaymentService paymentService;

    OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

Now:

```java
PaymentService payment = new CreditCardPayment();

OrderService service = new OrderService(payment);
```

The dependency is **given to** `OrderService`.

That's dependency injection.

Spring automates this object wiring.

Imagine:

Implementation:

# 42. `toString()`

Default:

```java
System.out.println(employee);
```

usually produces a class-name/hash-style representation.


# 43. `equals()`

Used to determine logical equality.

```java
Employee e1 = new Employee("John");
Employee e2 = new Employee("John");
```

Depending on implementation:

```java
e1.equals(e2)
```

can determine whether they represent the same logical employee.

---

# 44. `==` vs `equals()`

Extremely important.

For objects:

```java
e1 == e2
```

checks whether both references point to the **same object**.

```java
e1.equals(e2)
```

checks logical equality according to the class's implementation.

Example:

```java
String a = new String("Java");
String b = new String("Java");
```

```java
a == b
```

→ `false`

```java
a.equals(b)
```

→ `true`

---

# 45. `hashCode()`

If you override:

```java
equals()
```

you generally need to correctly override:

```java
hashCode()
```

Important rule:

> If two objects are equal according to `equals()`, they must have the same hash code.

This becomes very important with:

```text
HashMap
HashSet
HashTable
```

and therefore enterprise Java.

# 46. Immutability

An immutable object cannot have its state changed after creation.

Example:

```java
String
```

is immutable.

Conceptually:

```java
String name = "Java";

name = "Spring";
```

doesn't modify the original `"Java"` object.

A common immutable class:

```java
final class Employee {

    private final String name;

    Employee(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}
```

No setter.

# 56. SOLID Principles ⭐⭐⭐⭐⭐

Once basic OOP is understood, learn SOLID.

```text

O → Open/Closed Principle
L → Liskov Substitution Principle
I → Interface Segregation Principle
D → Dependency Inversion Principle
```

Especially:

### Dependency Inversion Principle

High-level code should depend on abstractions rather than concrete implementations.

Instead of:

```java
class OrderService {

    private CreditCardPayment payment =
            new CreditCardPayment();
}
```

prefer:

```java
class OrderService {

    private PaymentService payment;

    OrderService(PaymentService payment) {
        this.payment = payment;
    }
}
```

This is directly connected to Spring's dependency injection philosophy.

---

# 57. Coupling

Understand:

### Tight coupling

```java
class OrderService {

    CreditCardPayment payment =
            new CreditCardPayment();
}
```

OrderService is strongly tied to one implementation.

### Loose coupling

```java
class OrderService {

    private PaymentService payment;

    OrderService(PaymentService payment) {
        this.payment = payment;
    }
}
```

Now:

```text
OrderService
      ↓
PaymentService
      ↑
 ┌────┴─────┐
Card       UPI
```

This is exactly the type of design you'll see throughout Spring.

---

# 58. Cohesion

Cohesion means how closely related the responsibilities of a class are.

Bad:

```java
class Employee {

    void calculateSalary() {}

    void sendEmail() {}

    void connectToDatabase() {}

    void generateReport() {}
}
```

Too many responsibilities.

Better:

```text
EmployeeService
EmailService
ReportService
EmployeeRepository
```

This leads directly to good Spring architecture.

---

# 59. IS-A vs HAS-A

Memorize this.

### IS-A → inheritance

```text
Dog IS-A Animal
```

```java
class Dog extends Animal
```

### HAS-A → composition

```text
Car HAS-A Engine
```

```java
class Car {
    Engine engine;
}
```

### USES-A → dependency

```text
OrderService USES-A PaymentService
```

```java
class OrderService {
    PaymentService paymentService;
}
```

This terminology is frequently used in Java interviews.

---

# 60. The Complete Mental Model

You should eventually be able to look at code like:

```java
@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void placeOrder() {
        paymentService.pay();
    }
}
```

and understand **every OOP concept involved**:

```text
@Service
   ↓
Spring annotation

OrderService
   ↓
class

paymentService
   ↓
reference variable

PaymentService
   ↓
interface / abstraction

OrderService HAS-A PaymentService
   ↓
composition

constructor
   ↓
constructor injection

PaymentService injected
   ↓
dependency injection

   ↓
polymorphism

actual implementation
   ↓
runtime method dispatch

private final
   ↓

```

That is the level you should reach before starting serious Spring Core.
